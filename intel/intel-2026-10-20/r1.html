01

Pi API beta 接管了哪些工作

Physical Intelligence 在公告中指出，即使已有机器人基础模型，把它适配到新任务、环境或机器人，仍需要机器学习基础设施、算力和数据处理流程。Pi API beta 提供的产品路径，是让开发者上传数据，由 Pi 管理微调所需的算力与基础设施，并通过托管网关访问微调后的模型。

这项设计的意义在于把反复搭建训练与推理服务的工作交给平台。任务选择、机器人硬件，以及采集什么示范、怎样测试和怎样补齐失败案例，仍属于公告所描述的应用开发过程。它降低的是接入与迭代的基础设施负担，不能仅凭 API 的存在推断任务已经解决。

02

从示范到下一轮改进

公告披露的是开发流程，没有公开模型内部的完整训练方法。按已披露内容，这个循环可拆成四步。

  1. 收集并上传示范数据 团队围绕自己的应用采集示范，将数据交给 API。公告列举的难点包括衣物翻到反面、食材留不在勺中、制造零件落到错误位置。它们说明需要补的数据取决于具体失败，而不是只增加任意示范。

  2. 在托管基础设施上微调 上传的数据用于微调 π 模型，计算资源与训练基础设施由 Pi 管理。该页面没有给出微调的损失函数、哪些参数更新、哪些模块冻结，因而不能从这份产品公告还原算法训练链。

  3. 调用模型并在机器人上测试 开发者经托管网关使用微调后的模型进行推理，并在自己的机器人上测试表现。页面未列出推理请求包含哪些图像、指令或附加状态，也未说明返回的是何种动作表示及其如何连接底层控制器。这些接口细节仍未知。

  4. 用失败指导下一轮采集 团队根据机器人测试中的失败决定接下来采集什么数据，再进入训练与评估。这里明确披露的是开发者组织的迭代循环，不能把它理解成机器人无需人工参与便自动在线更新模型。

03

两类案例分别证明到哪一步

  • Almond 的零件去毛刺 公告展示双臂机器人 Axol 为自身装配所用的间隔件去毛刺，使用团队通过 Pi API 迭代四天后获得的模型。四天描述的是这次模型迭代过程，不能换算为单次训练时长或单件加工节拍。页面也没有给出去毛刺合格率、重复试验数量或连续运行时长。

  • Actor 的重型机械作业 公告称，Actor 的自主轮式装载机在一次真实商业部署中铲取物料并装入自卸卡车，机器内没有操作员。这是来源方对该案例的描述。驾驶室内无人不能独自证明全程无需远程支持，页面也未提供接管频率或长期可靠性统计。

两个案例体现了不同应用方向，但没有统一的对照实验与统计口径，不能据此横向比较性能。Almond 的四天迭代也不能套用到 Actor 的商业部署。

04

云端部署还要看哪些条件

页面称，多数展示应用通过 API 使用云端托管推理，部分早期部署暴露了网络连接问题。因此，理解这些案例时必须保留云端连接这一条件，不能将它们直接当作离线运行能力的证明。

本页未公布端到端延迟、断网处理方式、统一成功率、价格或服务可用性承诺。现有材料支持的是产品流程与案例展示。下一步值得跟踪的是具体硬件与接口要求、连续运行中的失败和接管记录，以及网络波动时的表现。
